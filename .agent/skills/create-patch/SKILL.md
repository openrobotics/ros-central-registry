---
name: create-patch
description: Roll up in-place edits made via vendor-module into one or more new, immutable Bazel module versions ready to commit as a PR. Use this once you've fixed and tested a package's vendored source and are ready to turn it into a mergeable change; also use it if you're not sure which vendored packages you actually touched.
---

`//tools/ci:create_patch` diffs your vendored edits against **raw** upstream
(not the currently-published version — every `.rcr.N` patch describes a
transformation relative to the same original archive, not an incremental
delta), and writes the result as a new module version.

- If the module's current version has already reached `main` (checked via
  local git, see `--base-ref` below), this **increments** to a brand-new
  version directory, e.g. `rclcpp@32.0.0-1.rcr.1` -> `rclcpp@32.0.0-1.rcr.2`.
- If the current version only exists on your branch (never merged), this
  **amends it in place** instead — running `create_patch` again after more
  edits doesn't mint another throwaway version.

Requires a workspace already generated by `setup-workspace`, with at least
one package vendored and edited via `vendor-module`.

## Fixing one specific package

```shell
# from the repo root, not inside workspace/
bazel run //tools/ci:create_patch -- rclcpp
```

This is deterministic and non-interactive: it either creates exactly one new
`modules/rclcpp/<new-version>/` directory, or prints "No changes detected"
and does nothing.

## Not sure which vendored packages you actually edited?

Omit the module name. This is the right choice whenever you've vendored
several packages (or a whole `--variant`/`--all`) and only touched some of
them:

```shell
bazel run //tools/ci:create_patch --   # no module argument
```

This auto-detects every vendored module with real local edits (cheaply,
via the file-hash manifest `vendor-module` records — no network fetch for
packages you didn't touch), prints a summary per changed package, then asks
for one confirmation before rolling all of them up:

```
Detected changes in 2 vendored module(s):
Creating rclcpp@32.0.0-1.rcr.2 (from 32.0.0-1.rcr.1):
  patches: 1 (was 0)
  overlay: 0 (was 0)
Creating rclcpp_action@10.2.1-2.rcr.1 (from 10.2.1-2):
  patches: 0 (was 0)
  overlay: 1 (was 0)
Roll up 2 module(s) into new patch versions? [y/N]:
```

Useful flags in this mode:

- `--yes` / `-y` — skip the confirmation (e.g. running non-interactively).
- `--dry-run` — print what would happen (works in both modes) without
  writing or prompting.
- `--base-ref` (default `main`) — the local git ref a version must already
  exist at to be treated as published/immutable. Checked against your
  **local** ref only, not `origin/<ref>` — keep it up to date yourself, or
  the amend/increment decision below can be wrong.

When amending a branch-only version in place, the summary line reads
"Amending X@V in place (branch-only, not yet published)" instead of
"Creating X@V (from Y)".

## What your PR should look like

Exactly the new (or, if amended in place, the same) version directory/
directories under `modules/<package>/`, plus the corresponding
`metadata.json` updates (a new entry appended to `versions`) — nothing else,
and no other package's files. It's fine for a branch-only version's
directory to show a history of several in-place amendments across your
commits — CI only ever sees the final state, diffed against `main`, where
it's brand new either way. But **never** touch a version directory that's
already on `main`, with two exceptions: (1) `metadata.json` files can be
modified to add versions or yanked versions, and (2) `MODULE.bazel` files
can have their version argument bumped by exactly one patch suffix (any
other edits are forbidden). Edits to `rosdistro`'s `MODULE.bazel` are exempt
from the version-bump-only rule, on `main`-published versions too.
`tools/ci/check_pr_modules.py` enforces this in CI and will fail the PR otherwise (see the immutability rule in `AGENTS.md`).

**Never include `MODULE.bazel.lock`**: A module's patch/overlay must never include a `MODULE.bazel.lock` file (neither under `overlay/` nor referenced in `source.json`). Lockfiles belong only to consumer or root workspaces and must never be published with a module.

When you open the PR, fill out every section of
`.github/PULL_REQUEST_TEMPLATE.md` (GitHub applies it to the description
automatically) — in particular:

- **Packages affected** — name the package(s) you just rolled up.
- **Generative AI disclosure** — if you are the agent that produced this
  patch (or materially assisted with it), disclose that honestly per the
  linked OSRF Generative AI policy; don't leave it blank or answer "No" on
  its behalf.
- **Related issue** — link the issue this patch fixes, if any.

## Pre-patch Cleanliness and Validation

Before running `create_patch` and committing:
1. **Remove reject/conflict artifacts**: Ensure no `.rej`, `.orig`, or temporary conflict files exist under `workspace/vendor/<module>+/`. If left behind, `create_patch` will treat them as new overlay files and write them to `source.json`, causing `check_pr_modules.py` and CI builds to fail.
2. **Verify copyright header order**: Ensure the `# Copyright ...` header comment block is at the very top (line 1) of every `BUILD.bazel` and `.bzl` file, **before** any `load(...)` statements. Never prepend a `load(...)` statement above the copyright header.
3. **Format build files**: Run `buildifier -mode fix -r .` from the repo root so all new and modified `BUILD.bazel`/`.bzl` files adhere to formatting standards (and if you run `buildifier` on files under `modules/<pkg>/<ver>/overlay/` after `create_patch`, make sure to re-run `create_patch` or regenerate `source.json` integrity hashes afterwards).
4. **Validate modules**: Run `bazel test //tools/ci/...` (and `check_pr_modules`) locally. This verifies that all overlay and patch hashes in `source.json` match disk files exactly, immutability rules are respected, and no undeclared or missing files exist.

## Gotchas

- **`MODULE.bazel.lock` generated in vendored source** — Bazel invocations in
  `workspace/` or `workspace/vendor/<module>+/` may generate `MODULE.bazel.lock`.
  `create_patch` ignores `MODULE.bazel.lock` automatically so it is never added
  as an overlay or diffed, and it should never be manually committed to `modules/`.
- **Stray `.rej` or `.orig` files captured as overlays** — If patch rebase left `.rej` files in the vendor directory, delete them before running `create_patch`.
- "This workspace resolved X to A, but the latest published version is B" —
  the workspace is stale (someone else's patch to that package merged since
  you set up the workspace). Re-run the `setup-workspace` skill, then
  `vendor-module` again, before creating the patch — don't hand-adjust
  version numbers.
- "does not exist. Run 'bazel run //tools/ci:vendor_modules -- <module>'
  first" — you haven't vendored that package in this workspace yet; go back
  to the `vendor-module` skill.
- "modules/X/V/ has changed on disk since this workspace vendored it" —
  something else touched that not-yet-published version directory since you
  vendored (typically a concurrent `git pull`/checkout/rebase). This refuses
  rather than guessing, since blindly overwriting could silently discard
  whatever changed it. If you have no local edits worth keeping, re-run
  `vendor-module`; if you do, use the `rebase-module` skill instead.
- "No package-directory snapshot found for X" — same drift-detection guard,
  but the snapshot itself is missing (e.g. an old workspace from before this
  check existed). Re-run `vendor-module`.
- If auto-detect mode finds nothing, either nothing was actually edited, or
  the edits exactly match what's already published — both are reported and
  are not errors.
