description: Generate a throwaway Bazel workspace for a specific RCR release, so you can build/test the full distribution or a variant of it, or set the stage for vendor-module/create-patch. Use this first, before vendor-module, whenever a task involves building, testing, or patching packages in this repo.

Every "do something with a released set of packages" task in this repo starts
here. `//tools/ci:setup_workspace` reads a `ros` release's transitive
dependency set out of `modules/`, and materializes a self-contained Bazel
workspace under `workspace/` (gitignored) that pins every package to its
resolved version.

## When to use this skill

- Before building or testing a whole ROS variant (`ros_core`, `ros_base`,
  `desktop`, `desktop_full`, `perception`, `simulation`).
- As step 1 of fixing a bug in a package (see `create-patch` and
  `vendor-module` skills for steps 2/3).
- Whenever a workspace might be stale — i.e. it's been a while since you ran
  this, and someone else might have merged a patch to a package you depend
  on in the meantime. Re-running is always safe and cheap.

## Command

```shell
bazel run //tools/ci:setup_workspace -- --release=lyrical.2026-06-08.rcr.2
```

Find the current release name at the top of `README.md`, or by looking for
the highest `.rcr.N` directory under `modules/ros/`. `--workspace-dir` (default
`workspace`) lets you point at a different directory if you need more than one
concurrently.

## What it produces

- `workspace/MODULE.bazel` — pins every package in the release, plus
  `single_version_override()`s for any package that already has a newer
  published patch than what the release pins (printed as an `OVERRIDE:`
  line — this is what lets two developers patch the same package in the
  same week without colliding on the same next version number).
- `workspace/.bazelrc` — hermetic toolchain flags, remote cache config, and a
  `common:<variant> --target_pattern_file=ros-<variant>.txt` entry per
  variant.
- `workspace/ros-<variant>.txt` — one target-pattern file per variant
  (`core`, `base`, `desktop`, `desktop_full`, `perception`, `simulation`),
  each listing every package in that variant as `@pkg//...`.

## Using the generated workspace

```shell
cd workspace
bazel build --config perception   # or --config core, base, desktop, ...
bazel test  --config perception
```

The first build compiles the whole selected variant from source and is slow;
subsequent builds are incremental. To work on one specific package instead of
a whole variant, don't build the whole config — go straight to the
`vendor-module` skill.

## Gotchas

- Never hand-edit anything under `workspace/` expecting it to persist — it's
  fully regenerated by this command and is gitignored.
- The six variant names here (`core`, `base`, ...) are the `--config` flag
  values and the `ros-<name>.txt` filenames. `//tools/ci:vendor_modules`'s
  `--variant` flag takes the *package* names instead (`ros_core`, `ros_base`,
  `desktop`, `desktop_full`, `perception`, `simulation`) — see the
  `vendor-module` skill. Don't mix the two up.
- If `bazel run //tools/ci:vendor_modules` or `//tools/ci:create_patch` later
  complain the workspace is stale, the fix is to just re-run this command,
  not to hand-patch version numbers. But if you have uncommitted edits in a
  vendored package you don't want to lose, use the `rebase-module` skill
  instead of re-running this directly — it re-baselines for you while
  preserving your edits.
